# Webots 1200 秒零停滞、零重规划修复 Workflow

## 最终目标

在 Webots Scene C、8 台机器人、高任务到达率条件下连续运行至少 1200 仿真秒，所有正常移动都由统一联合滚动规划提前协调，不依赖运行期重新规划脱困。

最终验收必须同时满足：

- `total_replans == 0`；
- 日志中 `Replan`、`replan requested`、`stalled ... replanning` 均为 0；
- `_command_reverse`、physical escape、teleport recovery 调用均为 0；
- `rapid_route_overrides == 0`；
- `pair_distance_violations == 0`；
- 不出现碰撞、控制器异常、世界加载 ERROR；
- 不存在持续超过 10 秒的非计划停止；
- 机器人处于 `EN_ROUTE_PICKUP`、`CARRYING`、`EN_ROUTE_DELIVERY`
  或其他任务执行状态时，不得出现非计划停止不动；
- 合法的预约等待必须带有明确的 joint plan wait action、开始时间和结束时间，
  且不计作停止不动；没有有效等待预约却没有净位移的情况一律判为停滞；
- 每台机器人至少完成 1 个任务；
- 1200 秒内持续产生任务完成记录，不能以全体停车换取零 replan；
- 联合规划 P95 小于 200 ms，且 Webots 无明显周期性卡顿。

任一指标不满足，整次 1200 秒运行判定失败，不允许用平均值、短时运行或人工观察替代。失败后必须保留首个失败证据，返回对应实现步骤继续修改、测试、两轮双人审查和 Webots 验证，直到通过为止。

## 每一步的强制质量门禁

每个步骤必须严格按以下顺序完成：

1. 明确本步骤修改范围、失败指标和回滚点；
2. 完成实现及针对性自动测试；
3. 运行完整测试集；
4. Code Review 第一轮：至少两位独立审查者分别检查；
5. 修复第一轮全部阻断问题并重新运行完整测试；
6. Code Review 第二轮：至少两位独立审查者再次复审修复后的代码；
7. 两位审查者在第二轮均明确 `PASS` 后，才允许运行 Webots；
8. 执行本步骤规定的 Webots 时长，解析日志和结果 JSON；
9. Webots 指标不通过则回到本步骤第 2 项，不得进入下一步。

审查者不能只确认测试通过，必须检查状态机、异常路径、性能退化、版本/epoch、一致性和 Webots 实际执行语义。

## 步骤 0：冻结可重复基线和零重规划计数器

实现内容：

- 固定 Scene C、FCFS、8 台机器人和 seed；
- 给所有可能触发路线变化的入口建立独立累计计数；
- 区分初始规划、任务阶段正常切换、滚动计划续接和 replan；
- replan 计数必须覆盖 Supervisor、robot controller、恢复器和紧急逃逸；
- 保存每次路线写入的 source、epoch、version、robot、时间和原因。

自动测试：验证每一种 replan/escape/override 都无法漏计。

Webots 门禁：90 秒运行，指标和日志计数必须一致；本步骤只冻结基线，不要求 replan 为 0。

## 步骤 1：联合滚动规划成为唯一正常路线规划器

实现内容：

- 每次规划必须包含全部活动机器人；
- 使用真实当前位置、朝向、速度、暂停状态和最终业务目标；
- 生成固定滚动窗口内的时空轨迹，包括等待、错峰、绕行和目标驻留；
- 规划窗口必须在旧窗口耗尽前续接；
- 单机器人规划器不得再独立修改活动路线。

自动测试：对向会车、十字交叉、追尾、窄口、宽路绕行、8 机器人连续任务流。

Webots 门禁：150 秒，联合方案持续续接成功；旧 replan 写入口调用为 0。

## 步骤 2：滚动窗口执行与真实进度重锚

实现内容：

- 控制器区分“滚动窗口结束”和“业务目标到达”；
- 每轮以机器人真实位置和执行进度重锚，禁止沿用已经过期的预计位置；
- DWA、peer slowdown、转向和临时 hold 造成的迟到必须进入下一轮时间模型；
- 窗口续接失败时执行安全等待，不允许单机 replan；
- 下一联合窗口激活前，当前安全窗口必须仍有效。

自动测试：执行迟到、ACK 延迟、某机器人暂停、窗口候选超时、重复窗口和旧 epoch。

Webots 门禁：200 秒，窗口断档为 0、部分激活为 0、replan 为 0。

## 步骤 3：清除旧路线写入与恢复竞争

实现内容：

- 预测冲突只能请求下一次全组联合规划，不得直接写路线；
- DWA 只能输出短时速度，不得替换 waypoints；
- stall monitor 只记录诊断，不得执行普通 replan；
- `_command_reverse`、physical escape 和 teleport 在正常运行配置中关闭；
- 所有路线写入必须来自已确认的联合 plan epoch 或正常业务阶段初始接入。

自动测试：扫描所有路线写入口；任何未授权 source 写入必须失败并被计数。

Webots 门禁：300 秒，`total_replans=0`、escape=0、override=0、安全违规=0。

## 步骤 4：预判能力和高负载稳定性

实现内容：

- 在任务分配前评估新任务对全体轨迹的影响；
- 新任务仅在存在可持续联合窗口时激活；
- 对拥堵区域使用预约、等待区和方向错峰；
- 宽阔区域允许自由空间绕行，避免人工走廊造成假死锁；
- 规划失败采用保持当前安全轨迹并在下一周期继续求解，不触发 replan。

自动测试：任务突发、8 台满载、目标交换、多个机器人同时穿越中心区域、长期公平性。

Webots 门禁：450 秒，replan=0，所有机器人持续取得净进展且至少出现多次任务完成。

## 步骤 5：600 秒预验收

在进入最终耐久测试前，先执行一次 600 秒完整预验收。其硬指标与最终验收一致：

- replan 为 0；
- 任务执行期间非计划停滞为 0；
- escape、override、安全违规为 0；
- 每台机器人至少完成 1 个任务。

600 秒预验收失败时不得进入 1200 秒测试，必须返回失败所属步骤继续修改。

## 步骤 6：最终 1200 秒验收

固定条件：

- Scene C；
- 8 台机器人；
- FCFS；
- 固定 seed 42；
- fast/no-rendering 自动运行；
- `SMART_FACTORY_SIM_DURATION >= 1200`；
- 自动停止并生成完整 JSON 和 stdout/stderr 日志。

执行顺序：

1. 完整自动测试集通过；
2. 第一轮两位独立 Code Review 均 PASS；
3. 第二轮两位独立 Code Review 均 PASS；
4. 运行至少 1200 秒 Webots；
5. 自动解析日志和结果 JSON；
6. 对照“最终目标”逐项判定。

最终只允许输出两种结论：

- `PASS`：1200 秒内所有硬指标全部满足，并附日志、JSON 和测试结果；
- `FAIL_CONTINUE`：列出第一个失败时间、机器人、任务状态、最后净位移、
  合法等待状态、路线版本、plan epoch 和触发源，然后返回对应步骤继续修复；
  不允许在失败状态下结束整个修复流程。

在获得 1200 秒 `total_replans == 0` 且任务执行期间非计划停滞为 0 的真实 Webots 结果之前，禁止使用“已彻底修复”“机器人不会再卡住”等表述。
