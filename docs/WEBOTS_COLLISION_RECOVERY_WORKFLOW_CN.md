# Webots 碰撞恢复修复工作流

本工作流针对 450 秒 Webots 运行中出现的固定近距离互锁、急停重规划请求丢失和指标不一致问题。每个实施步骤必须经过两轮代码审查、单元回归和真实 Webots 验证，任一项失败都返回当前步骤继续修复。

## 验收闭环

每一步严格执行：实现 → 第一轮 review（控制流、状态所有权、失败路径）→ 修改 → 单元测试 → 第二轮 review（并发时序、恢复闭环、指标）→ 修改 → 全量测试 → Webots 验证。

## 硬性验收条件

- 急停上报的重规划请求必须被尝试；冷却期间不得丢失。
- 合法 pending、dispatch delay 和 hold 不计入停滞；急停中的活动导航必须接受恢复监控。
- 成功下发的运行时替换路径计入 `total_replans`。
- 每次采样距离低于 0.50 m 时，必须存在可追溯的 safety event 和机器人编号。
- 场景 C 连续运行至少 450 秒，最小车距不低于 0.50 m；活动机器人不得在无合法等待原因时连续 30 秒无进展。
- 正式验收保持 `SMART_FACTORY_ENABLE_NONPHYSICAL_RECOVERY=0`。
